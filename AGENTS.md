## Commands (Makefile)
Для всех операций используй цели из `Makefile`:
- `make setup` — установка зависимостей и окружения (poetry/uv)
- `make test` — запуск pytest (юнит и CLI-тесты)
- `make lint` — проверка стиля и типов (ruff, mypy)
- `make build` — сборка CLI-пакета

## Project Structure
- `src/hztz/cli/` — точки входа CLI-команд (`audit`, `ask`, `decompose`, `chat`)
- `src/hztz/core/` — доменная логика, работы с LLM, парсеры
- `src/hztz/models/` — Pydantic-модели состояния (`decomposition.json`)
- `src/hztz/templates/` — шаблоны рендеринга Markdown (`decomposition.md`)
- `tests/` — тесты (`tests/fixtures/` для образцов ТЗ и JSON/MD)

## Architectural Invariants
1. **State vs View (JSON + MD):**
   - Единым источником правды (State / AST) является `decomposition.json`. Все статусы, графы зависимостей (`depends_on`), Gaps и Open Questions хранятся строго в JSON.
   - Файл `decomposition.md` — это исключительно представление (View / Rendered Output). Не пытайся парсить бизнес-состояние только из `.md`.
2. **Единая система ID:**
   - `T#` — Tasks / Blocks (атомарные блоки декомпозиции)
   - `G#` — Gaps (технологические и бизнес-пробелы)
   - `O#` — Open Questions (открытые вопросы для аналитика)
   - `A#` — Audit findings (замечания аудита)
3. **Паттерн генерации вопросов (`hz ask`):**
   - Никаких абстрактных вопросов. Команда всегда формирует 2–3 конкретные инженерные развилки (Trade-offs / Option A, B, C) с последствиями каждого выбора.

## Rules of Engagement for Coding Agent
- **Исправляй причину, а не следствие:** При сбоях или ошибках тестов ищи корневую проблему в моделях данных или контрактах, а не подгоняй вывод костылями.
- **Игнорируй чужие изменения:** Если в рабочей директории есть правки, которые ты не делал в текущей сессии — не трогай их и не пытайся «навести порядок».
- **Переиспользуй существующие типы:** Перед созданием новой модели или DTO проверь `src/hztz/models/`. Не создавай параллельные сущности-дубликаты.
- **Справочные примеры:** При изменении структуры декомпозиции или шаблонов ориентируйся на эталоны в `tests/fixtures/`.























# Repository Guidelines

`hztz` — CLI-инструмент, который находит неопределённости в ТЗ, превращает их
в вопросы с вариантами решения и режет спецификацию на блоки для реализации.

## Структура проекта

- `hztz/cli/` — команды Typer: `audit`, `ask`, `decompose`, `chat`, `task`, `gap`.
- `hztz/core/` — доменная модель: `Gap`, `Question`, `Task`, статусы, граф зависимостей.
- `hztz/detectors/` — категории дефектов требований (по одному модулю на категорию).
- `hztz/prompts/` — промпты в отдельных файлах; в коде промптов быть не должно.
- `hztz/providers/` — адаптеры LLM (openai, anthropic, ollama) за общим интерфейсом.
- `hztz/render/` — вывод в `md`, `json`, plain text.
- `tests/` — pytest; фикстуры спецификаций в `tests/fixtures/`.

## Команды

Используй make-цели, не shell-команды напрямую.

- `make setup` — окружение и зависимости
- `make test` — полный прогон тестов
- `make lint` — ruff + mypy
- `make fmt` — форматирование
- `make run ARGS="audit spec.md"` — локальный запуск CLI

## Архитектурные инварианты

1. **`audit` — единственный источник ID.** `G{n}`, `O{n}`, `T{n}` создаются только там.
   `ask` и `decompose` читают готовый `gaps.json`, а не сканируют спецификацию заново.
2. **`.json` — состояние, `.md` — нарратив.** Статусы, зависимости и ID живут в JSON;
   объяснения, примеры кода и лог решений — в Markdown. Дублировать состояние в `.md` нельзя.
3. **JSON меняется только командами** (`hztz task done T3`, `hztz gap resolve G1`),
   никогда прямой записью из другого слоя.
4. **Терминология внешняя, не выдуманная.** Категории дефектов — по ISO/IEC/IEEE 29148
   (`unambiguous`, `complete`, `verifiable`, `consistent`, `feasible`).
   Новые категории не изобретаем.
5. **`severity` и `confidence` — разные поля.** Не сводить в одну шкалу.
6. **Вывод LLM валидируется по схеме** перед записью в `.json`. Невалидный ответ —
   ошибка, а не «починим как-нибудь».
7. **`blocked_by` (открытый gap) ≠ `depends_on` (порядок реализации).** Разные поля,
   разная логика в `next`.

## Соглашения

- Промпт = файл в `hztz/prompts/`, имя совпадает с детектором или командой.
- Новый провайдер LLM реализует существующий интерфейс, а не заводит свой.
- Эталонный тест для новой команды — `tests/test_audit.py`.
- Конфиг по умолчанию — `~/.hzrc`; флаги CLI только переопределяют его.

## Правила работы

- Исправляй причину, а не следствие.
- Перед новой сущностью найди существующую модель данных и расширь её.
  Параллельные структуры не создавай.
- Если видишь изменения, которые ты не делал — игнорируй их, не откатывай.
- Не добавляй зависимость без явной необходимости.
